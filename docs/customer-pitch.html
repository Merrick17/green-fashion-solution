UX & End-to-End Flow Demonstration

This document is not a sales brochure. It is a practical walkthrough for the app owner to validate exactly what we built, how users move through the product, and where the handoffs happen.

Objective of this document

  • Show the full UX structure by portal (Public, Customer, Designer, Admin)
  • Show real lifecycle flows and decision points
  • Make demos consistent for stakeholder and owner reviews
  • Align what is already shipped vs what is next

Core principle

Customer and Designer never communicate directly. Admin is the only bridge.

AI scope

AI supports customer moodboards and admin proposal drafting only. Final decisions remain human.

2. Main Product Lifecycle

Project flow from intake to completion

Step 1 — Customer: Create Project and upload inspiration files.
Step 2 — Customer: Build/iterate moodboard canvas with AI assistance.
Step 3 — Admin: Review project and assign tasks/briefs to internal designers.
Step 4 — Designer: Upload fabric/product references to internal asset library.
Step 5 — Admin: Build proposal from curated assets (AI-assisted draft + manual control).
Step 6 — Customer: Approve / Reject / Request changes and select inspiration items.
Step 7 — Admin: Revise proposal if needed, schedule Teams meetings, and move status.
Step 8 — Admin + Customer: Track Sampling → Production → Completed.

Lifecycle statuses visible in project timeline

Draft → Submitted → In Review → Sourcing → Proposal Ready → Sampling → Production → Completed

UX outcome: every persona sees only the screens relevant to its role, but all screens align on the same project lifecycle.

  • Project-centric navigation prevents context loss

4. Internal UX Walkthrough (Designer + Admin)

How execution is controlled behind the scenes

Designer UX

  • Upload fabric and product references with keywords
  • Manage personal asset library and assigned work
  • Complete tasks generated by admin
  • Boundary: no customer data visibility

Admin UX

  • Projects board and detailed project control
  • Task assignment and lifecycle progression
  • AI-assisted proposal drafting + final manual submission
  • Meetings approvals and calendar orchestration
  • User management, audit, leads, files, notifications

Critical handoff points

Handoff System behavior
Customer inspiration → Admin review Moodboard + project context available to admin in one flow
Admin tasking → Designer uploads Assets become proposal inputs; still invisible to customer until curated
Admin proposal → Customer decision Status transitions: sent / approved / rejected / changes requested
Customer revision request → Admin rebuild Selected inspiration context can prefill next proposal pass

5. AI Experience in UX

Where AI appears for users

Customer-facing AI

  • AI moodboard assistant in canvas workflow
  • Image parsing and structured board augmentation
  • AI image generation into moodboard context

Admin-facing AI

  • Proposal assistant panel for pre-drafting proposal content
  • RAG-backed context from project assets/history to improve suggestions
  • Admin keeps final approval and submission control
UX rule: AI assists creation speed, but it does not bypass role boundaries or business approvals.

7. Demo Script for Owner Review

How to present the product in 20–25 minutes

Minute 1–3: Public landing and auth (show value proposition and role entry).
Minute 4–9: Customer creates project + opens moodboard canvas + uploads inspiration.
Minute 10–13: Switch to Admin, assign tasks, open proposal builder, show AI assist.
Minute 14–17: Switch to Designer, upload fabric/product assets, show task context.
Minute 18–20: Back to Customer, review proposal and make decision.
Minute 21–23: Show meetings request/approval and timeline status progression.
Minute 24–25: Show settings (preferences/export) and close with roadmap.

Owner acceptance checklist

  • Can we demonstrate all three role portals clearly?
  • Can we show one complete lifecycle from project intake to proposal decision?
  • Can we prove boundary rules (no customer/designer cross-visibility)?
  • Can we show operational confidence (notifications, meetings, audit)?
